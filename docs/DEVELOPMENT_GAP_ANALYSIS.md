### 1.1 확인된 문서 관계

- 중복 분석 문서는 사용자가 정리했으며 현재 문서는 Y를 대표 자료로 참조합니다. 동기화 충돌 사본은 독립된 근거로 계산하지 않습니다.
- Y는 다른 AI의 분석 응답을 보관한 자료입니다. 영상의 직접 설명, 다른 웹 자료에서 보충한 내용, 분석자의 해석이 섞여 있으므로 제품 기능이 실제로 존재한다는 증거로 사용하지 않습니다.
- P는 2026-06-08 기준 정적 분석이라고 명시합니다. 당시의 코드 라인 수, 테스트 수, 문제 진단을 현재 구현 사실로 옮기지 않습니다.
- P의 테스트 커버리지 35~40%는 실행 측정 근거가 제시되지 않았습니다. 무한 로그 증가 우려도 곧바로 메모리 누수가 확인됐다는 뜻은 아닙니다. Rhai와 CLI의 `read-only` 옵션을 연결한 대목도 실제 격리가 입증된 것으로 취급하지 않습니다.
- V10/V11의 RN 선택적 도입, Agy 비활성, 약관 관련 제한은 V12에서 명시적으로 변경하거나 제외한 결정입니다. 이를 누락으로 분류하거나 자동 복원하지 않습니다.

### 1.2 판정 기준

- **누락:** 참고 자료의 요구를 수용할 도메인이나 실행 절차가 V12에 없습니다.
- **구체화 필요:** 원칙 또는 기능은 있지만 구현자가 동일한 동작을 만들 수 있을 만큼 계약과 실패 처리가 정해지지 않았습니다.
- **정합성 조정:** V12 내부의 인터페이스·우선순위·단계가 서로 다르게 해석될 수 있습니다.

각 항목의 문서 근거는 확인 사실입니다. §0의 확정 결정 외에 보완 방향, 우선순위와 수용 기준은 설계 제안입니다. 원자료의 요구, 사용자의 결정, 구현을 위해 도출한 설계를 구분했습니다.

## 2. 전체 판단

V12는 범용 Task·Run·Workspace·Artifact·Validation을 구분하고, 실행과 통신의 책임을 나누는 기본 구조를 갖췄습니다. Managed/Attached 구분, 메시지 전달과 작업 완료의 분리, 검증 버전 고정, RN Fork 유지 전략도 이미 포함되어 있습니다. 이 내용을 다시 신규 기능으로 제안할 필요는 없습니다.

부족한 부분은 작업 전후와 장애 시점의 구체적인 계약입니다. 특히 다음 연결이 약합니다.

1. **작업 시작 전:** 어떤 지침·자료·환경을 읽었으며 무엇이 부족한지 확인하는 절차.
2. **작업 사이:** 아직 생성되지 않은 선행 산출물을 후속 입력에 연결하는 규칙과 동기 위임의 대기·자원 관리.
3. **검증·승인 시점:** 어떤 결과와 어떤 외부 행위를 검증·승인했는지 고정하는 계약.
4. **작업 종료 후:** 실행 기록에서 재사용 지식을 선별하고 다음 실행에서 찾는 절차.
5. **운영 중:** 중단·중복·지연 이벤트, Core 장애, 로그 증가, 설정 충돌을 처리하는 규칙.

## 4. 항목별 분석

### GAP-01. 실행 전 맥락 수집을 명시적인 단계로 정의해야 합니다

**근거:** Y §2.1과 §5.1은 기존 지침, 파일 구조, 현재 Git 상태를 먼저 읽는 절차를 강조합니다. V12 §4.3에는 목표·제약·입력 Artifact가 있고 `GIT-03`은 Base Commit·Dirty 검사를 요구하지만, 공통 맥락 수집 계약은 없습니다. §7.4의 Context Capsule은 주로 인계에 관한 예시입니다.

**보완 제안:** Run 시작 전에 `ContextSnapshot`을 고정합니다. 적용 지침의 위치·버전·출처, 입력 Artifact 버전, Host·Workspace, 필요한 도구와 버전, 코딩 작업의 Git 상태를 포함합니다. 모든 파일을 모델에 넣는 방식 대신 선택 기준과 제외 범위를 둡니다. 지침 충돌과 읽기 실패를 드러내고, 외부 자료의 본문을 실행 정책으로 승격하지 않습니다.

**수용 기준:** 같은 Task를 다시 실행했을 때 각 Run이 어떤 자료와 설정을 사용했는지 비교할 수 있습니다. 필수 지침이나 입력을 읽지 못하면 조용히 생략하지 않고 실패 또는 질문 상태로 전환합니다. 비Git 작업에도 적용됩니다.

### GAP-02. 실행 이력과 재사용 지식을 별도로 관리해야 합니다

**근거:** Y §2.4와 §5.1은 의사결정·학습 결과를 다음 세션에서 찾을 수 있게 보존하는 루프를 제시합니다. V12에는 DB·이벤트·세션 재개·Context Capsule이 있지만, 실행을 넘어 재사용할 지식을 선별·검색·수정하는 절차는 없습니다.

**보완 제안:** `DecisionRecord` 또는 `KnowledgeEntry`에 프로젝트 범위, 근거 Artifact/Run, 적용 조건, 검토 상태, 생성·수정 시각, 대체·폐기 관계를 둡니다. 작업 종료 시 지식 후보를 만들고, 사용자 설정에 따라 검토·저장합니다. 다음 실행의 관련 지식 검색을 GAP-01에 연결합니다. 프로젝트 지침 파일 수정 권한과 일반 결과 파일 생성 권한을 구분합니다.

**수용 기준:** 새 Native Session에서도 검토된 관련 결정을 찾아 출처와 함께 제시할 수 있습니다. 오래되거나 반려된 지식은 제외됩니다. 에이전트의 추측이 검토 없이 프로젝트 규칙이 되지 않으며, 저장·삭제·수정 경로가 있습니다.

### GAP-03. 재사용 Workflow와 시각적 편집기를 분리해야 합니다

**근거:** Y §3.1은 수동 업무를 반복 가능한 단계와 Skill로 추출하는 기능을 제시합니다. V12 §12 Phase 3은 Workflow 템플릿과 시각적 편집기를 함께 P2로 묶습니다.

**보완 제안:** 파일 기반 `WorkflowTemplate`을 P1로 분리합니다. 입력 파라미터, Task/의존성, Output·Validation 계약, 역할 기본값, 요구 Capability, 템플릿 버전을 정의합니다. 실행할 때는 별도의 Plan 인스턴스를 만들고 템플릿 변경을 기존 Run에 소급하지 않습니다. 기존 실행에서 템플릿 초안을 추출하는 기능은 그 이후에 둡니다.

**수용 기준:** 조사→교차 검토→보고서 같은 흐름을 다른 입력과 Provider로 재실행할 수 있습니다. 재사용이 과거 승인이나 권한의 재사용을 뜻하지 않으며, 실행 시 적용한 템플릿 버전을 조회할 수 있습니다.

### GAP-04. 입력 부족과 근거 부족을 처리하는 규칙이 필요합니다

**근거:** Y §4.1은 데이터 정합성과 절차 문서화를 선행 조건으로 제시합니다. V12 §4.2와 §11.2에는 조사·분석 작업 및 출처 확인이 있으나, 누락·충돌·오래된 입력을 다루는 계약과 주장별 근거 연결은 부족합니다.

**보완 제안:** Task별 필수 입력, 원본 위치·버전·확인 시각, 알려진 가정, 해결되지 않은 질문을 정의합니다. 필요 시 `InputReadiness` 검사에서 중단·질문·제한적 실행을 선택합니다. 조사 결과는 확인 사실·추론·미확인 주장을 구분하고 핵심 주장에 `EvidenceRef`를 연결합니다. 외부 문서의 지시는 분석 내용으로 다룹니다.

**수용 기준:** 필수 데이터가 없을 때 임의 값을 채워 통과시키지 않습니다. 형식과 출처 항목이 있다는 이유만으로 사실 검증을 통과한 것으로 표시하지 않습니다. 자료의 상충이나 검증 한계를 결과에 남깁니다.

**적용 범위:** 원자료의 ‘빈도가 낮은 업무는 도입 보류’ 같은 조언은 운영 선택 기준으로만 다룹니다. 일회성 조사·문서 작업까지 제품에서 차단하는 규칙으로 옮기지 않습니다.

### GAP-05. 산출물 명세와 후속 입력을 연결할 수 있어야 합니다

**근거:** Y §2.1과 §5.1은 구체적인 결과물을 사전에 정의하도록 합니다. V12 §4.4의 `ArtifactSpec`에는 `type`, `contentType`, `required`만 있습니다. `TaskSpec.inputArtifacts`는 이미 존재하는 ID 배열이며 `dependencies`는 Task ID 배열입니다.

**문제 해석:** 선행 Task가 아직 만들지 않은 특정 출력과 후속 Task의 입력을 어떻게 연결하는지 예시 타입만으로 표현하기 어렵습니다. 파일 종류만 정하면 예상 경로·개수·JSON Schema·내용 조건과 검증 대상도 불명확합니다.

**보완 제안:** 출력에 논리 이름과 계약 ID를 두고, 경로/형식/Schema/필수 여부/허용 개수를 지정합니다. 입력은 기존 Artifact 참조와 `producerTaskId + outputName` 참조를 구분합니다. 실행 시 실제 Artifact 버전에 바인딩하고 바인딩 결과를 저장합니다. 승인·검증에는 변경 가능한 원본 경로보다 고정된 버전이나 스냅샷을 사용합니다.

**수용 기준:** ‘초안 작성 Task의 `draft` 출력을 리뷰 Task의 입력으로 사용’하는 계획을 실행 전에 표현할 수 있습니다. 출력 누락·형식 불일치·변경된 입력을 구별하며, 재작업 시 이전 산출물과 새 산출물을 혼동하지 않습니다.

### GAP-06. Validation 종류와 실제 적용 프로파일 사이를 채워야 합니다

**근거:** Y §2.2~§2.3은 작은 검증 단위와 시각적 검토를 강조합니다. V12 §4.6은 Validator 종류를 잘 구분하지만, 어떤 변경에 어떤 검사·리뷰가 필요한지와 실행 중 체크포인트는 정하지 않습니다.

**보완 제안:** 코딩·문서·분석별 기본 검증 프로파일을 두고 변경 범위와 작업 정책에 따라 선택합니다. 문서/UI에는 렌더 결과나 스크린샷을 Evidence Artifact로 연결할 수 있게 합니다. 독립 Reviewer의 판정 형식, 근거, 수정 요청을 정하고 검증 오류·검증 실패·판정 불가를 구분합니다. 단계 중간 검증은 별도 하위 Task 또는 Checkpoint로 모델링합니다.

**수용 기준:** 파일 생성·명령 성공·내용 검토가 각각 구분됩니다. 필수 Validator 실행 자체가 실패하면 검증 통과가 되지 않습니다. 렌더 검토를 요구한 Task는 실제 렌더 근거와 판정 없이 통과하지 않습니다.

**범위 제한:** 모든 사소한 수정에 동일한 검사 묶음을 강제하지 않습니다. 재작업 때 재검사할 범위와 최종 통합 검증 범위를 계약으로 정합니다.

### GAP-07. 승인을 특정 결과와 특정 행위에 묶어야 합니다

**근거:** Y §2.5는 발송 큐와 변경 전후 비교를 제시합니다. V12의 `VERIFY-03`, `SAFE-05`, Approval UI와 `approvals` 표에는 승인 개념이 있지만 승인 범위·유효기간·변경 시 처리 계약은 부족합니다.

**보완 제안:** 계획 승인, 결과 검토 승인, 외부 변경 실행 승인을 구분합니다. 승인에는 Task/Run, Artifact 버전, 실행할 행위·대상·인자, 승인자, 시각, 정책 버전과 유효 조건을 연결합니다. 대상이나 내용이 바뀌면 필요한 승인을 다시 계산합니다. 코드 Diff뿐 아니라 문서 변경·구조화 데이터 변경·외부 요청의 미리보기를 제공합니다.

**수용 기준:** 초안 A를 승인한 뒤 내용 B가 실제 발송되는 상황을 차단합니다. 승인 반려·만료·철회·중복 클릭을 정의하며, 일반 결과 승인만으로 추가 외부 행위가 허용되지 않습니다. Provider가 실행 중 승인 응답을 지원하지 않으면 해당 사실과 가능한 후속 절차를 명시합니다.

**확정 운영:** DEC-03에 따라 승인 요청을 마스터가 총괄합니다. 승인자는 사용자 또는 위임 범위 안의 마스터일 수 있으며 결정 주체를 구분해 기록합니다. 모든 계획·결과·Worker 요청마다 사용자 승인을 강제하지 않습니다. 사용자에게 남겨 둔 판단과 권한 확대 요청은 GAP-20의 흐름으로 처리합니다.

### GAP-08. Provider Adapter와 외부 업무 도구 Connector를 구분해야 합니다

**근거:** Y §3.2는 인박스·CRM·견적 추적·주간 보고서의 다중 도구 수집을 설명합니다. V12는 `automation` Task와 명령 실행을 포함하지만 외부 도구에 대한 공통 계약은 없습니다. §5의 Provider Connector는 세션 연결용이므로 이 용도로 확장하면 책임이 섞입니다.

**보완 제안:** 업무 도구용 Connector의 도입 여부와 범위를 명시합니다. 채택한다면 읽기/변경 Capability, 계정·프로젝트 범위, Schema, 오류, 속도 제한, 자격 증명 참조를 정의합니다. 변경 행위에는 `ActionProposal`을 만들어 준비→검토/정책 검사→실행→결과 확인을 연결합니다. 도구가 제공하는 멱등성과 실행 후 조회 기능을 Capability로 드러냅니다.

**수용 기준:** 로컬 Mock으로도 초안 준비와 실제 변경을 구분하고, 실행 직후 연결이 끊어진 경우 중복 실행 전에 외부 상태를 확인할 수 있습니다. 외부 시스템의 보장이 없는데 정확히 한 번 실행된다고 주장하지 않습니다.

**확정 범위:** DEC-01에 따라 초기 제품은 파일·CLI 중심입니다. 메일/CRM Connector는 후속 확장으로 두고 위 계약은 향후 연결 경계로 남깁니다. 초기 실행의 필수 조건으로 요구하지 않습니다.

### GAP-09. 이벤트 대기와 장기 업무의 종료 조건을 모델링해야 합니다

**근거:** Y §3.2의 견적 후속 연락은 시간 경과와 회신 감지에 따라 멈춥니다. V12는 Task DAG, Timeout, 메시지 TTL은 정의하지만 Trigger·대기·반복 업무 계약은 없습니다.

**보완 제안:** 수동/예약/외부 이벤트 Trigger와 실행 인스턴스를 구분합니다. `WaitingEvent`, `nextWakeAt`, 이벤트 중복 제거 키, 대기 기한과 자동 중단 조건을 정의합니다. 긴 대기는 모델 프로세스와 실행 슬롯을 점유하지 않게 합니다. 반복은 한 DAG에 순환 간선을 넣는 대신 상위 Workflow의 새 실행 또는 명시적인 제한된 반복으로 표현합니다.

**수용 기준:** 동일 이벤트 재수신이 중복 작업을 만들지 않고 재시작 후 대기를 복원합니다. 회신 도착 뒤 예약된 후속 연락을 취소합니다. 예약을 지원할 때 시간대, 놓친 실행, 중복 기동 정책이 정해져 있습니다.

**확정 범위:** DEC-01에 따라 외부 이벤트·예약 자동화는 후속 확장입니다. 현재의 Task 대기·Timeout·비동기 위임은 기본 실행에 포함하며 외부 Trigger 기능과 구분합니다.

### GAP-10. 상태 머신의 예외와 경합을 표로 확정해야 합니다

**근거:** V12 §7.1은 기본 경로를 보여주지만 `Blocked` 작업의 취소, `Validating` 중 취소, 승인 반려·만료, 선행 Task 실패, 검증 후 Artifact 변경을 상태 전이로 모두 설명하지 않습니다. §14에는 복구·중복 위험이 있으나 원자적 처리 규칙은 없습니다. P의 실패 복구 우려도 이 검증 필요성을 뒷받침하는 과거 자료입니다.

**보완 제안:** Task·Run·Approval·Delivery 상태를 분리한 전이 표를 작성합니다. 각 전이에 트리거, 사전 조건, DB 갱신, 후속 효과, 실패 시 복구를 명시합니다. 취소와 늦은 완료 이벤트의 우선순위, 재시도 이후 도착한 이전 Run 이벤트 처리, 선행 실패 시 후속 차단/건너뛰기 정책을 정합니다. 상태 갱신과 외부 호출 사이에는 작업 의도 기록·멱등성·재조정 절차를 둡니다.

**수용 기준:** 취소된 이전 Run의 완료 이벤트가 새 Run을 완료시키지 않습니다. 검증 대상 변경 시 필요한 검증과 승인이 무효화됩니다. 외부 행위의 실제 성공 여부가 불명확한 경우 맹목적으로 재실행하지 않고 조회·재조정 또는 사용자 판단으로 전환합니다.

### GAP-11. 동기 위임이 실행 슬롯과 잠금을 어떻게 사용하는지 정해야 합니다

**근거:** V12 §1.1은 동기·비동기 위임을 목표로 하고, §7.3은 MCP 도구와 깊이·동시성 제한을 제시합니다. V10/V11도 동기·비동기 위임을 참고 기능으로 들지만 자식 완료를 기다리는 부모의 자원 처리는 정하지 않습니다.

**문제 해석:** 동시성 1에서 부모가 슬롯을 점유한 채 자식을 기다리면 자식이 실행되지 않을 수 있습니다. 부모가 Writer Lock을 보유한 Workspace를 자식도 요구하는 경우도 별도 처리해야 합니다. 이는 현재 구현의 확인된 버그가 아니라 설계상 시험할 경합 시나리오입니다.

**보완 제안:** `delegate_task`는 먼저 Task ID를 반환하는 방식으로 고정하고, 동기 대기는 Core의 별도 대기 계약으로 정의합니다. 부모 대기 동안 Provider 슬롯과 전체 활성 Task 수를 구분하며, 잠금 이전·별도 Workspace 사용·거부 중 정책을 정합니다. 부모 취소 시 자식과 자손의 처리, 전체 시간·호출·위임 예산을 상속 규칙으로 정의합니다.

**수용 기준:** 동시성 1에서도 지원하는 위임 흐름이 진행하거나 즉시 설명 가능한 오류로 끝납니다. 무한 대기와 Writer 중복을 허용하지 않습니다. 중복 MCP 요청이 같은 자식 작업을 여러 번 생성하지 않습니다.

### GAP-12. 공통 Adapter 계약을 실제 제어 흐름에 맞춰 보완해야 합니다

**근거:** V12 §7.2는 Core의 Run ID 발급을 설명하지만 §6.1 `startTask(task)`는 Run ID를 반환하며 실행 문맥 입력은 없습니다. `approval_required` 이벤트에는 응답 API가 없고, `steerRunningTask` Capability에도 대응 메서드가 없습니다. §6.5 이벤트에는 Tool 호출·Turn·순서 식별자가 부족합니다. V11 §6.6에 있던 `TaskResult` 타입도 V12에는 책임 설명만 남아 있습니다.

**보완 제안:** Core가 발급한 `RunContext`를 Adapter에 전달하고 Native Session/Turn ID를 반환하게 합니다. 후속 입력·승인 응답·취소·강제 종료·결과 조회의 지원 범위와 오류를 정의합니다. Tool 호출 ID, 이벤트 순서, Provider 원본 ID를 연결합니다. 시작 직후 이벤트가 구독 전에 발생하는 경우를 버퍼 또는 재조회 계약으로 처리합니다. `TaskResult`와 `DeliveryReceipt`의 최소 Schema를 함께 둡니다.

**Capability 제안:** `boolean`만 두지 말고 필요 시 지원/미지원/미검증, 대상 버전·Host, 확인 시각, 제한 사유를 표현합니다. 실행에 필요한 최소 탐지는 P0, 고급 UI와 동적 탐색은 P1로 나눌 수 있습니다.

**수용 기준:** 같은 Run에 실행 이벤트·산출물·최종 결과가 일관되게 연결됩니다. 취소 요청 접수와 실제 종료 확인이 구분됩니다. 미지원 제어 요청은 묵시적으로 무시되지 않습니다. 이 계약은 Provider의 현재 지원 기능을 검증한 결과가 아니라 설계 요구입니다.

### GAP-13. UI 종료, Core 장애, 세션 재사용을 별개로 다뤄야 합니다

**근거:** V12 §3.4는 독립 서비스와 실행 위치를 제안하고, §10은 `sessions`에 `run_id`를 둡니다. §6에는 지속형 다중 턴과 세션 재개가 있어 Session·Run·Turn의 관계를 더 정해야 합니다. RN 장애 시 Managed Run 유지와 Core 자체 장애는 서로 다른 문제입니다.

**보완 제안:** Host/프로젝트별 Core 인스턴스 소유권, 시작·종료·상태 확인, IPC 접근 범위, 로그·DB 경로를 정합니다. Managed Process의 감독 주체와 Core 재시작 뒤 생존 확인·출력 회수·유실 판정을 정의합니다. 하나의 Session을 여러 Run에서 재사용할지, 초기에는 Run당 새 Session만 허용할지 결정합니다. 재사용한다면 Run↔Session↔Turn 연결과 동시 사용 잠금을 모델링합니다.

**수용 기준:** VS Code Reload와 Core 강제 종료 시험의 기대 결과가 각각 정해집니다. 같은 프로젝트를 여러 창에서 열어도 의도하지 않은 이중 Scheduler가 생기지 않습니다. PID만으로 세션 정체성을 확정하지 않습니다. Remote SSH의 실행 Host와 로컬 UI Host를 구분합니다.

### GAP-14. RN 설치·설정 변경 관리의 구체성을 회복해야 합니다

**근거:** V11 §6.7은 사용자 설정 백업·Diff·복원, 기존 MCP 이름 충돌을 명시합니다. §6.4는 `push`/`turn`/`pull`의 처리 정책을 표로 설명합니다. V12에는 `RN-POC-01`, Capability, Upstream 관리가 있으나 설치 시 설정 소유권과 Tier별 실행 정책은 더 추상적입니다.

**보완 제안:** 자체 Task MCP와 RN MCP의 네임스페이스, Provider별 등록·해제, 변경 전 미리보기·백업, 설치 후 사용자 수정과의 병합, 제거 시 프로젝트가 추가한 항목만 정리하는 규칙을 둡니다. Core–RN RPC의 로컬 접근 권한·접속 주체도 명시합니다. Attached 실행은 Tier별 대기·Timeout·수동 개입 정책으로 연결합니다.

**수용 기준:** 설치 전에 있던 MCP/Hook 설정과 설치 후 사용자가 추가한 설정이 제거 과정에서 보존됩니다. `turn`/`pull` 세션에 요청했다고 즉시 실행된 것으로 표시하지 않습니다. 메시지 수신 승인과 실행 승인은 계속 별개입니다.

**유지할 결정:** RN Fork를 표준 통신 인프라로 쓰는 V12 결정을 유지합니다. V11의 선택적 Sidecar 모델로 되돌리자는 제안이 아닙니다.

### GAP-15. 설정 위치와 권한의 해석 순서를 정해야 합니다

### GAP-19. 세션 포크와 문맥 전달을 토큰 효율 정책에 포함해야 합니다

**추가 요청:** 사용자가 에이전틱 작업의 토큰 효율을 위한 세션 포크를 설계 항목에 포함하도록 요청했습니다. 기존 V12의 Fork는 대부분 Reason Network 소스 저장소의 Fork를 뜻하며, 대화 세션을 분기하는 기능과 구분해야 합니다.

#### 19.1 구분할 개념

| 방식 | 동작 | 적용 목적 |
|---|---|---|
| `fresh` | 필요한 목표·자료만 전달해 새 세션을 시작합니다. | 독립 검토, 작은 작업, 불필요한 과거 문맥 배제 |
| `resume` | 기존 세션에서 후속 Turn을 실행합니다. | 같은 작업의 연속 실행·재작업 |
| `native-fork` | Provider가 지원하는 경로로 기존 대화의 특정 시점에서 별도 세션을 만듭니다. | 같은 기반 문맥을 사용하는 병렬 작업·대안 탐색 |
| `capsule` | 목표·결정·필요한 근거·Artifact 참조를 선별해 새 세션에 전달합니다. | 다른 Provider로 위임, 포크 미지원, 긴 이력 축소 |
| Prompt Cache | Provider가 일치하는 입력 Prefix의 처리 결과를 재사용합니다. | 조건이 맞을 때 입력 처리 시간과 과금 비용 감소 |

세션 포크와 Prompt Cache는 다른 기능입니다. 포크가 부모 이력을 복사하면 자식의 문맥 길이가 길어질 수 있습니다. 포크가 캐시 적중이나 무료 문맥 상속을 보장한다고 가정하지 않습니다. OS 프로세스의 Copy-on-Write와 같은 메모리 공유 의미도 부여하지 않습니다.

#### 19.2 공식 문서 확인 범위와 미검증 사항

아래는 2026-10-23 공식 문서를 확인한 결과입니다. 로컬 설치 버전에서 실행 시험한 결과는 아닙니다.

| Provider | 문서에서 확인한 인터페이스 | 구현 전 확인할 범위 |
|---|---|---|
| Codex | App Server의 `thread/fork`는 저장 이력을 새 Thread로 분기합니다. `lastTurnId`로 분기 지점을 지정할 수 있습니다. | 대상 버전의 Schema, 선택 시점의 지원, 문맥·설정 처리, 새 ID와 결과 이벤트 연결 |

#### 19.3 마스터가 선택하는 문맥 전달 정책

**설계 제안:** 마스터 에이전트가 위임할 때 `ContextPlan`을 결정하고 Core가 실행 전 검증합니다. 선택 사유와 대체 경로를 기록합니다.

1. 공통 지침·자료 분석을 한 번 수행한 뒤, 필요하면 완료된 Turn을 공통 분기 기준으로 고정합니다. 현재 확인한 Native Fork를 다른 Provider의 세션으로 직접 복제하는 수단으로 사용하지 않습니다.
2. 같은 Provider에서 공통 문맥 비중이 높고 Fork Capability가 검증됐다면 `native-fork`를 선택할 수 있습니다. Provider가 허용하는 분기 기준을 명시하고, 실행 중인 불완전한 Turn을 자동으로 확정된 기준처럼 사용하지 않습니다.
3. 다른 Provider로 위임하거나 포크 지원이 미검증이면 `capsule`을 사용합니다. 포크 실패를 숨긴 채 동일 동작인 것처럼 처리하지 않고 선택한 대체 경로를 기록합니다.
4. 전체 이력이 길거나 하위 작업이 작으면 필요한 자료만 담은 `fresh`/`capsule`을 선택합니다. 독립 Reviewer에게 구현자의 결론과 시행착오를 모두 상속하면 편향될 수 있으므로, 검토 계약과 대상 Artifact만 전달하는 방식을 우선 검토합니다.
5. 안정된 지침·도구 정의·공통 자료와 작업별 내용을 구분해 불필요한 Prefix 변경을 줄입니다. 캐시 적중을 위해 작업에 맞지 않는 권한·모델·도구 구성을 유지하지는 않습니다.
6. Worker는 구조화된 결과, 근거, 미해결 사항과 Artifact 참조를 반환합니다. 마스터가 모든 Worker의 전체 대화를 매번 읽는 구조를 기본값으로 두지 않습니다.
7. 마스터의 대화도 길어지면 Task·결정·검증 상태를 영속 기록하고 필요한 문맥만 유지합니다. 압축·요약 시 누락 가능성과 기준 시점을 기록합니다.

#### 19.4 세션 분기와 실행 격리의 경계

- 포크는 별도 Task/Run/Native Session ID와 계보를 갖습니다. `parentSessionId`, 분기 Turn 또는 지원 가능한 기준, Context Snapshot, 선택 전략, Provider 버전을 연결합니다.
- 대화 복제는 Workspace 파일이나 외부 시스템 상태의 복제가 아닙니다. 쓰기 작업에는 별도 Workspace 또는 Writer Lock 정책을 적용합니다.
- 포크된 세션의 실제 도구·경로·권한은 새 Task에 맞춰 다시 적용하고 확인합니다. 과거 대화에 기록된 허용이나 부모의 실행 이력만으로 새 권한을 부여하지 않습니다. 제한을 적용할 수 없는 Provider 조합은 거부하거나 지원 가능한 새 세션 전략으로 전환합니다.
- 부모가 수행했던 명령이나 외부 변경을 자식이 재실행하지 않도록 Task 계약, 실행 이력, 멱등성 검사를 유지합니다.
- 분기 깊이·개수·동시성·전체 작업 예산을 마스터가 관리하고 Core가 집행합니다. 무제한 재귀 Fork를 허용하지 않습니다.

#### 19.5 측정 기준과 도입 단계

**P0:** 공통 Context 전략과 Capability 계약을 정의하고 Native Fork PoC를 수행합니다. 미지원 Provider도 `capsule`/`fresh`로 기본 위임을 수행할 수 있어야 하며, 모든 Provider의 포크 성공을 MVP 선행 조건으로 두지 않습니다.

**P1:** 검증된 Native Fork를 통합하고 전략 선택과 문맥량을 최적화합니다. 비용 비교는 요청받은 같은 작업을 대상으로 새 세션·포크·Capsule의 결과 품질과 함께 측정합니다.

| 지표 | 집계 규칙 |
|---|---|
| 입력·출력 토큰 | 공통 준비, 모든 Worker, 마스터의 판단·취합, 실패·재시도를 포함합니다. Provider의 입력 합계에 캐시 토큰이 포함되면 다시 더하지 않습니다. |
| 캐시 읽기·쓰기 | Provider가 제공한 경우 구분하여 수집합니다. 캐시 읽기 비용이 0이라고 가정하지 않습니다. |
| 실제 비용·사용량 | API 비용, CLI 제공 추정치, 구독 사용량을 구분합니다. 미제공 값은 Unknown으로 둡니다. |
| 지연과 도구 호출 | 전체 완료 시간, 재조회·파일 재독해·중복 호출을 비교합니다. |
| 결과 품질 | 동일한 Validation Contract의 통과 여부와 재작업 횟수를 함께 비교합니다. |

Provider의 누적 사용량과 Turn별 증가량을 구분하고 원본 사용량 이벤트를 연결합니다. 캐시 적중률만으로 전체 비용 절감을 주장하지 않으며, 절감률은 실측 전 수치로 약속하지 않습니다.

**수용 기준:** 부모와 분기 세션의 후속 대화가 구분되고 기준 시점과 결과의 계보를 조회할 수 있습니다. 미지원 조합은 명시적으로 대체됩니다. 파일·권한·예산 경계가 유지되며, 같은 검증 기준으로 각 전략의 전체 사용량과 품질을 비교할 수 있습니다.

### GAP-20. 마스터 에이전트의 총괄 권한과 Core 집행을 연결해야 합니다

**확정 결정:** DEC-03에 따라 사용자는 마스터 에이전트를 통해 전체 작업을 통제합니다. Worker의 개별 실행·질문·승인 요청을 사용자가 직접 모두 조정하는 구조를 기본으로 두지 않습니다.

**역할 분담 제안:**

| 주체 | 책임 |
|---|---|
| 사용자 | 목표·제약·허용 범위 설정, 필요한 질문 응답, 개입·취소, 사용자 판단이 필요한 요청 처리 |
| 마스터 에이전트 | 계획, Task 생성·위임, Provider·Role·문맥 전략 선택, 예산 배분, Worker 요청 판단, 검증·재작업·최종 결과 통합 |
| Orchestration Core | 구조화 결정 검증, DAG·권한·예산 검사, 실행 큐·잠금, 상태 전이·영속화·감사, Provider별 제어 연결 |
| Worker | 배정한 Task 수행, 제한 안에서 하위 위임 요청, 결과·근거·추가 요청 보고 |
| RN Fork | 기존 책임인 세션 발견·메시지 전달·Presence 유지 |

마스터는 논리적 역할이며 특정 Provider나 모델을 영구 고정하지 않습니다. 사용자에게서 받은 목표와 권한, 진행 상태는 Core에 기록하여 마스터 세션이 바뀌어도 이어갈 수 있게 합니다. 위임과 포크는 서로 다른 기능이므로 Worker를 모두 Native Fork로 만들어야 한다고 가정하지 않습니다.

**승인·개입 흐름 제안:**

1. Worker 요청은 Task/Run, 행위·대상·인자, 필요한 권한, 근거와 함께 Core에 접수합니다.
2. Core가 현재 정책과 권한을 확인하고 마스터가 위임받은 범위 안에서 허용·거부·조건 변경·대체 작업을 결정합니다. 범위 안의 요청을 일괄적으로 사용자 확인에 올리지 않습니다.
3. 권한 확대, 명시적으로 사용자에게 남겨 둔 결정, 정보 부족으로 판단할 수 없는 요청은 마스터가 이유와 선택지를 정리해 사용자에게 올립니다. 마스터 판단만으로 사용자 권한을 확대하지 않습니다.
4. Core가 결정의 유효성과 실제 Provider 제어 지원을 확인한 뒤 적용합니다. 실행 중 승인 응답을 지원하지 않는 Provider는 허용된 대안으로 재계획하거나 미지원 사유를 보고하며, 승인 API가 존재한다고 가정하지 않습니다.
5. 결정 주체, 정책 버전, 대상 결과·행위, 적용·거부 결과를 기록합니다. 마스터의 일반 자연어 응답을 검증 없이 실행 명령으로 처리하지 않습니다.

**복구와 예산:** 마스터 장애 시 기록되지 않은 지시는 실행하지 않습니다. 이미 허용된 Run의 유지·중단과 마스터 재개 정책을 정하고, 재접속 뒤 같은 지시를 중복 실행하지 않게 합니다. 전체 Task의 시간·동시성·위임·토큰 예산에는 마스터의 판단과 재시도도 포함합니다.

**수용 기준:** Worker 승인 요청을 마스터가 권한 안에서 처리하고 사용자 개입이 필요한 요청만 이유와 함께 전달합니다. 허용 범위를 넘는 마스터 결정은 Core가 차단합니다. 마스터 재개 후 Task·승인·결과가 중복되지 않으며, UI에서 어떤 주체가 결정했는지 확인할 수 있습니다.

## 7. 후속 설계 작성 순서

1. **기존 결정을 유지할 범위부터 고정합니다.** 범용 Task, 세 Provider의 Managed 우선, RN Fork, 실행/통신 분리, VS Code 우선, 기술 검증 중심 범위는 유지합니다.
2. **마스터 총괄과 최소 실행 계약을 보완합니다.** 마스터 결정·Core 집행, Context·입출력 연결·Run/Session·결과·승인·상태 전이·동기 위임을 정합니다. 세션 포크는 공통 계약과 PoC부터 진행하고 미지원 Provider의 대체 전략을 마련합니다.
3. **새 구현의 운영 계약을 정합니다.** 설정, 설치, 서비스 수명, 로그 한도를 구체화합니다. 기존 코드는 보존하되 재사용·호환·이관을 새 구현의 제약으로 두지 않습니다.
4. **확정한 범위에 따라 확장 기능을 배치합니다.** 재사용 지식·파일 기반 템플릿과 검증된 포크 최적화는 P1, 업무 Connector·외부 Trigger는 P2에 둡니다. 초기에는 파일·CLI 작업을 대상으로 합니다.
5. **요구사항 표·단계별 체크리스트·수용 시험을 같은 범위로 맞춥니다.** 세 Provider 동등 지원 목표와 실제 검증 상태를 구분하고, 기능별 버전·Host·시험 근거를 남깁니다.

후속 설계는 마스터가 작업을 총괄하는 구조 위에서 ‘어떤 문맥과 권한으로 실행했고, 어떤 결과를 검증·승인했으며, 중단 뒤 무엇을 신뢰하고 어떤 비용으로 다시 진행할 수 있는가’를 구현 가능한 계약으로 채웁니다.
