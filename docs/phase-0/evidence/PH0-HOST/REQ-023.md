## 1. 재현과 결과

같은 공용 런타임을 사용하는 일회용 소유 프로세스를 강제 종료하는 회귀 시험을 추가했습니다. 소유자의 `Drop`이나 정상 취소 경로는 실행되지 않습니다.

## 2. Linux 구현

변경 파일은 `crates/adapters/src/runtime/unix.rs`·`linux_guard.rs`와 HOST 소유 시험 경로입니다. Windows 실행 코드는 바꾸지 않았습니다. 새 Crate·실행 파일·의존성·서비스 등록·서버 설정·공통 계약 변경은 없습니다.

1. `Command`의 exec 전 자식이 실행별 감시 프로세스가 됩니다. 감시 프로세스에만 `PR_SET_CHILD_SUBREAPER`를 설정하고 실제 Provider를 fork·exec합니다. Core 전체의 subreaper 설정은 바꾸지 않습니다.
2. Provider는 감시 준비와 분리가 끝났다는 Gate를 받은 뒤에만 exec합니다. 감시 프로세스는 Provider Group에서 빠지고, Core의 직접 자식으로 남아 `getppid()` 변화를 10ms 간격으로 확인합니다. 이는 생성한 Tokio 스레드의 종료와 Core 프로세스의 종료를 구분합니다.
3. Core 유실 또는 Provider 종료 시 Provider Group을 종료하고, 고아가 되어 감시 프로세스로 재부모화된 자식을 반복해서 종료·회수합니다. `setsid`를 사용한 자식도 이 경로로 처리합니다.
4. `/proc/thread-self/children`은 경합 때문에 완전한 Snapshot으로 취급하지 않습니다. 재부모화 뒤 다시 읽고, **`waitpid`의 `ECHILD`를 확인해야** 회수 완료를 기록합니다.
5. 원래 Provider의 PID와 종료 상태를 유지합니다. 모든 자식을 회수했다는 별도 Receipt가 없으면 정상 회수로 판정하지 않습니다. 감시 프로세스 자체를 강제 종료한 시험에서도 오류를 확인했습니다.
6. 감시 PID를 Provider PGID로 사용해 Core가 감시 프로세스를 회수할 때까지 PGID를 예약합니다. `19f8666`에서는 `WNOWAIT`로 마지막 그룹 신호 이전의 PID 회수를 막고, 신호와 회수도 같은 Mutex로 직렬화했습니다. 회수한 PID를 다시 신호 대상으로 사용하지 않습니다.
7. fork 뒤 감시 경로는 할당·Rust 잠금·로그를 사용하지 않습니다. 불필요한 FD는 닫고 Receipt FD만 유지합니다. `close_range`가 없는 커널에는 fork 전 얻은 FD 한도까지 닫는 대체 경로가 있습니다. subreaper 또는 필요한 `/proc` 경로를 준비하지 못하면 Provider exec 전에 실패합니다.

`PR_SET_PDEATHSIG`만 추가하는 안은 채택하지 않았습니다. 생성 스레드가 끝났을 때도 신호가 발생하고 fork 자식에 상속되지 않아, 이 런타임의 스레드 수명과 손자 프로세스 문제를 함께 해결하지 못합니다. cgroup/systemd 필수 의존성과 재시작 후 PID 재탐색도 도입하지 않았습니다.

근거: [subreaper 의미](https://www.man7.org/linux/man-pages/man2/PR_SET_CHILD_SUBREAPER.2const.html), [부모 종료 신호의 제한](https://www.man7.org/linux/man-pages/man2/PR_SET_PDEATHSIG.2const.html), [children 파일의 경합](https://www.man7.org/linux/man-pages/man5/proc_tid_children.5.html), [Rust pre_exec 제약](https://doc.rust-lang.org/stable/std/os/unix/process/trait.CommandExt.html#tymethod.pre_exec).

## 5. Spec 정합성과 한계

- 이번 변경은 Phase 0의 Core 유실 뒤 감독 없는 Managed 실행을 막는 처리입니다. Spec §14.2·§14.3의 DB 영속화, 재시작 시 미완 Run·Lock 대조, 결과 복구는 여전히 후속 P0 구현입니다. 이를 완료했다고 주장하지 않습니다.
- 감시 프로세스는 종료·회수만 담당합니다. Core 없이 실행을 계속 감독하며 출력·결정을 복구하는 P1 서비스를 구현한 것은 아닙니다. 이 방향의 Spec 변경은 요청하지 않습니다.
- Windows Job 경로와 Linux의 일반 사용자 프로세스·실제 도구·`setsid` 자식을 검증했습니다. macOS, 권한·PID Namespace 변경, 감시 프로세스까지 함께 유실되는 장애, OS가 종료시킬 수 없는 프로세스는 이번 성공 증거의 범위 밖입니다. 감시 유실은 별도 시험에서 미확인 오류로 처리했습니다.
- `/proc` 준비 실패와 오래된 커널의 `close_range` 대체 경로는 코드에 있으나 이번 Host에서 해당 실패 환경을 만들지는 않았습니다.
- INTEGRATION은 이 변경과 기존 §14.2의 Phase 0 한계를 함께 검토하고 REQ-023·G3 최종 상태를 결정합니다.
