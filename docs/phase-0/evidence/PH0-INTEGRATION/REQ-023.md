# REQ-023: Linux에서 Core가 비정상 종료돼도 Provider 프로세스가 감독 없이 계속 실행됨

| 항목 | 값 |
|---|---|
| 요청 | PH0-INTEGRATION (`claude-opus-5.5/session-c9336d2c`) |
| 처리 | **PH0-HOST**: 사용자 지시(2026-10-26) |
| 접수 | 2026-10-26, 기준 `main` `42ab747` |
| 근거 | [INTEGRATION 증거](README.md) §9.5 발견 1, Spec §3(프로세스 감독)·§14.2 "Core 비정상 종료" |
| 우선순위 | **G3 판정 전 필수**. 함께 처리: §9.3 후속 1(`discovery_environment` 두 벌 단언) |

## 1. 관찰 (`psyki-nas`, 2026-10-26)

정책 Core(PID 109370, 디버그 빌드 `1733bf3`)가 Claude Run `run-04a295fb27bece7f7aea1a6bb37dd901`(파일 5개를 차례로 쓰기)을 실행하던 중 INTEGRATION이 `kill -9 109370`을 보냈습니다.

| 시각 | 사건 |
|---|---|
| 01:54:06 | Run 시작, Claude PID 117764(Core의 자식, 별도 Process Group) |
| 01:54:16.4 | Core `kill -9` |
| 01:54:16~01:54:54 | Core가 없는데 Claude가 `part1~5.txt`를 모두 쓰고 스스로 종료 |
| 01:56:53 | 새 Core는 이전 Run을 `not_found`로 거부(Phase 0 메모리 기록) |

Core가 죽은 뒤의 부작용(파일 4개)이 어떤 Core 기록에도 남지 않았고, 사용자는 그 Run이 아직 무언가를 하고 있다는 것을 알 수 없었습니다.

## 2. 원인 추정 (코드 확인, 실행 검증 전)

- Windows(`crates/adapters/src/runtime/windows.rs`): Job Object에 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`를 설정합니다. Core 프로세스가 죽어 Job 핸들이 닫히면 OS가 자식 트리를 끝낼 것으로 **추정**합니다(같은 상황의 Windows 실행 결과는 아직 없음).
- Unix(`crates/adapters/src/runtime/unix.rs`): `process_group(0)`으로 자식을 새 Process Group에 둡니다. 취소·정상 종료 때는 Core가 그룹에 신호를 보내지만, **Core 자체가 죽으면 그룹을 끝낼 주체가 없습니다**. `PR_SET_PDEATHSIG` 같은 부모 종료 연동이 없습니다.

즉 같은 "Core 비정상 종료"에서 Windows와 Linux의 결과가 다를 가능성이 높습니다.

## 3. 요청

1. **Windows 재현:** Windows 로컬에서 같은 상황(실행 중인 Managed Run이 있는 Core를 강제 종료)을 만들어, 자식 Provider 프로세스와 그 하위 트리가 실제로 끝나는지 확인합니다. Provider는 Claude `haiku` 한 개면 충분합니다.
2. **Linux 대책 설계와 구현:** Core가 비정상 종료될 때 Linux에서도 Managed 프로세스 트리가 감독 없이 남지 않게 합니다. 후보와 판단 기준:
   - `PR_SET_PDEATHSIG`(자식 생성 직후 설정): 스레드 단위 동작·`exec` 이후 유지 조건·손자 프로세스에는 적용되지 않는 점을 확인
   - Core 생존 감시 프로세스 또는 cgroup(사용자 단위 systemd scope 등) 사용: 서버 설정 변경 없이 쓸 수 있는지
   - 재시작한 Core가 이전 Core의 남은 Process Group을 찾아 정리하는 방식(Spec §14.2 "재시작 시 미완 Run 확인"): Phase 0 범위에서 가능한지
   어떤 방식을 택하든, Provider의 손자 프로세스(도구 실행 등)까지 함께 끝나는지 확인합니다.
3. **Spec 정합성:** Spec §14.2의 P0 "Core 비정상 종료" 행과 §3의 감독 설명이 Windows·Linux에서 같은 결과를 보장하는지 검토합니다. 보장하지 못하는 부분은 Spec 변경 요청(INTEGRATION 소유)으로 올립니다. 예를 들어 Phase 0 한계로 명시하는 것도 선택지입니다.
4. **시험:** Windows·Linux 각각 "실행 중 Core 강제 종료 → 자식 트리 종료" 실환경 시험을 추가합니다. 기본 실행에서는 제외(`#[ignore]`)합니다. 서버 시험은 `psyki-nas`의 일회용 임시 폴더에서 하고, 시험 세션 ID를 기록합니다.
5. **함께 처리(§9.3 후속 1):** `crates/adapters/tests/discovery_environment.rs`의 "두 벌 설치" 단언(`installed.len() >= 2`)을 실패가 아닌 전제 조건 보고로 바꿉니다. 서버 확장이 한 벌로 정리돼(2026-10-25 22:18) 지금은 실패합니다. 한 벌이면 다중 버전 선택 경로가 검증되지 않았다고 출력합니다.

## 4. 작업 방식

- 최신 `main`에서 Branch `ph0/host-req023`, Worktree `D:\worktree\TelosWeaver\ph0-host-req023`를 만듭니다. 서버 시험은 `~/TelosWeaver-wt/host-req023`(detached HEAD, [지시서](G3_LINUX_ASSIGNMENTS.md) §1)에서 합니다.
- 결과는 `evidence/PH0-HOST/REQ-023.md`에 Windows·`psyki-nas` 행을 나눠 기록하고 INTEGRATION에 통합을 요청합니다. 실행하지 않은 시험을 통과로 적지 않습니다.
- 공용 런타임은 HOST 소유입니다. Provider Adapter나 Core 실행 감독(`crates/core`)을 고쳐야 하면 해당 소유자 또는 INTEGRATION에 범위를 알립니다.
- 배정표의 PH0-HOST 행·REQ-023 행 갱신 규칙은 기존과 같습니다(단독 커밋, §7 표 행 사이 빈 줄 금지).
