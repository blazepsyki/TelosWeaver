# REQ-024: 공통 Capability 키 계약 (G3 재검토 C1)

| 항목 | 값 |
|---|---|
| 요청 | PH0-INTEGRATION (`claude-opus-5.5/session-c9336d2c`) |
| 처리 | **Codex**: 사용자 지시(2026-10-26). 이 요청에 한해 PH0-CONTRACT 경로(`crates/schema/**`, `schemas/**`, `crates/adapters/src/lib.rs`)와 PH0-CODEX 경로를 수정합니다 |
| 접수 | 2026-10-26, 기준 `main` `de7669a` 이후 |
| 근거 | [G3 대조표](G3_ACCEPTANCE.md) §2.1 C1, Spec §7.1(Capability 상태·증거)·§7.2(`detect()`)·§2.1 원칙 7 |
| 우선순위 | 비차단(G3 조건 아님). Phase 1에서 Core가 Capability로 집행하기 전 필수 |

## 1. 문제

`AgentAdapter::detect()`는 `HashMap<String, Capability>`를 돌려주지만 키 목록은 Spec과 계약 어디에도 없습니다. 그래서 같은 기능을 Adapter마다 다른 이름으로 보고합니다.

| 의미 | Claude (`claude.rs`) | Antigravity (`agy.rs`) | Codex (`codex.rs`) |
|---|---|---|---|
| 신규 Managed 실행 | `managed_run` | `managed_run` | `managed` |
| 이벤트 스트림 | `event_stream` | `event_stream` | `stream` |
| 취소 | `cancel` | `cancel` | `cancel` |
| Native Resume | `native_resume` | `native_resume` | `resume` |
| Native Fork | `native_fork` | `native_fork` | `native_fork` |
| 실행 중 입력 | `send_input` | `send_input` | `send_input` |
| 실행 중 승인 응답 | `answer_approval` | `answer_approval` | `approval` |
| VS Code 목록 표시 | `vscode_listing` | `vscode_listing` | `vscode_listing` |

`AdapterError::UnsupportedCapability.capability`에도 자유 문자열이 쓰입니다(예: Codex `managed`·`approval`·`approval_authorization`, 공통 미지원 시험 대역 `unimplemented.rs`의 `cancel_run` 등 메서드 이름). Core·Extension이 Provider 공통으로 "이 Provider가 Resume을 지원하는가"를 조회할 수 없고, Spec §19.2의 "최소 Capability" 집행(AGENT-03)의 기반이 없습니다.

## 2. 요청 (단계별)

### 단계 A: 제안 (코드 변경 전)

1. 현재 세 Adapter·Core·Extension에서 쓰는 Capability 키와 `UnsupportedCapability.capability` 값을 모두 모아 표로 만듭니다(위 표를 출발점으로 검색해 누락을 채움).
2. 공통 키 목록을 제안합니다. 각 키에 대해 이름, 의미(어느 `AgentAdapter` 메서드·`SessionMode`·설정과 대응하는지), 필수 여부(Spec §19.1·§19.2 기준), 현재 이름과의 대응을 적습니다. 이름 규칙은 기존 다수형(`snake_case`, `managed_run`·`native_resume`·`answer_approval`)을 기본안으로 하고, 바꾸려면 이유를 적습니다.
3. 표현 방식을 비교해 하나를 권장합니다.
   - (a) `telos-schema`의 문자열 상수 모듈과 알려진 키 목록(Trait 시그니처 유지)
   - (b) `CapabilityKey` 열거형(`serde` `snake_case`)으로 `HashMap` 키를 바꿈(Trait 시그니처 변경)
   - 판단 기준: JSON Schema·TypeScript 생성 결과, Provider 고유 Capability(예: 미래의 실험 기능)를 넣을 여지, 기존 Adapter·시험 변경량, `UnsupportedCapability.capability`와의 일관성
4. 제안을 `docs/phase-0/evidence/PH0-CODEX/REQ-024.md`(제안 절)에 쓰고 Branch에 커밋한 뒤 **INTEGRATION에 검토를 요청하고 멈춥니다.** 키 목록은 Spec에 들어가므로 사용자 승인 뒤 INTEGRATION이 Spec §7.1을 개정합니다(AGENTS.md "Spec 변경은 코드보다 먼저 사용자와 합의").

### 단계 B: 구현 (Spec 개정 뒤)

1. `telos-schema`에 승인된 키를 정의하고 Contract 시험을 추가합니다(키 문자열 고정, 직렬화 형태). Schema가 바뀌면 `UPDATE_SCHEMAS=1 cargo test -p telos-schema --test json_schemas`로 `schemas/`를 갱신하고, Extension 생성 타입이 빌드되는지 확인합니다.
2. 방식 (b)라면 `crates/adapters/src/lib.rs`의 Trait 시그니처와 `unimplemented.rs`·공통 시험을 함께 바꿉니다.
3. **Codex Adapter만** 새 키로 옮깁니다(`codex.rs`, `codex/**`, Codex 시험). `UnsupportedCapability.capability`도 같은 키를 씁니다.
4. Claude·Antigravity Adapter의 전환은 각 담당이 합니다(Claude는 C2·C4 작업과 함께, Antigravity는 AGY 후속). 방식 (b)처럼 다른 Adapter가 컴파일되지 않게 되는 변경이면, 단계 A 제안에 그 영향과 순서를 적어 INTEGRATION이 함께 조정합니다.

## 3. 범위와 금지

- `CapabilityState`·`EvidenceLevel`·`Capability` 구조체의 의미는 바꾸지 않습니다. 키 목록만 정합니다.
- 각 Adapter의 판정 값(`supported`·`unverified` 등)은 이 요청에서 바꾸지 않습니다. Codex 판정 보정은 [C3 지시서](CODEX_CAPABILITY_FOLLOWUP.md)에서 합니다.
- Core(`crates/core/**`)는 Capability를 아직 집행하지 않습니다. 시험 대역 `unimplemented.rs`의 메서드 이름 기반 값(`cancel_run` 등)을 키로 바꿀지도 제안에 포함합니다. Core 수정이 필요하면 INTEGRATION에 범위를 알립니다.
- 모델 호출은 필요 없습니다.

- 배정표 갱신: 착수 시 §4 REQ-024 행과 PH0-CONTRACT 행(이 요청의 담당 Codex를 기록)·§7을 `main` 단독 커밋으로 기록합니다(§7 표 행 사이 빈 줄 금지). 단계 A 제출 때와 단계 B 완료 때도 같은 방식으로 기록합니다.
