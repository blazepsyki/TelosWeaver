현재 통합 담당은 배정표에 기록된 `claude-opus-5.5/session-c9336d2c`입니다. 요청의 채택·반려·대안 결정, 필요한 HOST/MASTER/EXT 협의, 계약 구현·재검증과 새 기준 Commit 배포는 해당 절차에 따라 처리합니다. 이 문서의 권장안은 구현 완료나 사용자 확정 결정으로 해석하지 않습니다.

## 2. 확인 근거와 분류

앞선 독립 검토에서 실제 공개 타입을 사용하는 임시 코드로 다음을 확인했습니다. 검사 시점의 코드 변경분은 `ae31eb2`에 포함되어 있으며, 제출안 기반 Commit까지의 후속 변경은 문서·운영 설정이어서 검토 대상 Rust 계약은 동일합니다.

| 분류 | 확인한 내용 | 해석 범위 |
|---|---|---|
| 재현 | 같은 ProcessHandle에서 wait Future와 terminate Future를 동시에 유지하면 E0499 | 현재 가변 대여 형태의 제약입니다. Actor 또는 취소 안전한 대기로 구현할 수 없다는 뜻은 아닙니다. |
| 타입·시험 확인 및 재현 | rejected 결과에 거부 사유 없이 task_created 효과를 넣어 역직렬화 가능, 기존 공통 시험도 거부와 생성 효과를 함께 사용 | 현재 공통 타입·시험의 허용 상태이며 실제 정책 엔진의 잘못된 집행을 확인한 것은 아닙니다. |
| 재현 | 가짜 토큰을 넣은 HelloParams의 Debug 문자열에 토큰 원문 포함 | 타입의 출력 동작입니다. 실제 토큰이 로그로 유출되었다는 뜻은 아닙니다. |
| 재현 | CreateTasksPayload 안 TaskSpec의 알 수 없는 중첩 필드를 넣어도 파싱 성공 | 최상위 deny_unknown_fields가 모든 중첩 타입에 전파되지 않는 현재 정책입니다. |
| 소스 확인 | OutputEvent는 Line/Overflow/Closed, 스트림 항목에 I/O 오류를 직접 표현하는 형식 없음 | 공용 런타임은 Stub이므로 실제 I/O 장애·출력 유실의 실행 결과는 아닙니다. |

앞선 재검증은 Windows에서 `cargo test --workspace --locked` 18개, Clippy·포맷 검사, Extension의 42개 타입 생성·빌드가 통과한 범위입니다. 이번 제출안 작성에서는 런타임·Provider·RN을 새로 실행하지 않았습니다. Contract 시험 통과를 실제 통합 성공으로 사용하지 않습니다.

## 3. 변경 요청

### REQ-002 대기·입력·취소의 동시성 계약

- **관련 작업:** PH0-HOST, PH0-INTEGRATION, PH0-CONTRACT. 소비자는 세 Provider입니다.
- **대상:** `crates/adapters/src/runtime/mod.rs`의 ProcessHandle, wait/write_stdin/close_stdin/terminate 계약과 공용 시험.
- **이유:** 모든 비동기 메서드가 `&mut self`를 요구하여 직접 병행 Future를 유지할 수 없습니다. 대기 Future를 중도 취소할 때의 안전성도 정해지지 않아 HOST와 Provider가 서로 다른 제어 방식을 가정할 수 있습니다.
- **요청:** 명령 Actor·분리된 제어 Handle 또는 취소 안전한 대기 방식 중 사용할 계약을 정합니다. wait 중단 뒤 재대기·입력·종료 요청, 반복 wait/terminate, 종료 직전 경합의 의미를 명시합니다. 현재 인터페이스를 유지해도 안전한 사용 패턴과 취소 안전성을 입증하면 됩니다.
- **호환 영향:** 공개 Trait 변경 시 세 Adapter의 사용 방식이 바뀝니다. CONTRACT가 인터페이스 영향을 검토하고 통합 담당이 기준 변경을 배포합니다. HOST가 미배정이면 먼저 담당을 확정하며 검토자가 대신 구현하지 않습니다.
- **수용 시험:** 대기 중 stdin 입력, 대기 중 취소, 유예 뒤 강제 종료, 대기 Future 중단 후 종료 회수, 반복 취소, 취소/자연 종료 경합. 교착·추적 유실·자식 잔존 여부를 확인합니다.
- **현재 상태:** 검토 대기. 공개 API 변경안은 미확정입니다.

### REQ-003 출력 오류와 상한 초과 처리

- **관련 작업:** PH0-HOST, 세 Provider, PH0-INTEGRATION. CONTRACT는 오류·이벤트 매핑을 확인합니다.
- **대상:** 같은 런타임 모듈의 OutputLimits·OutputEvent·take_output과 Provider 실패 분류 연결.
- **이유:** 출력 수집 도중의 I/O 오류를 정상 EOF와 구분하여 전달하는 명시적 스트림 항목이 없습니다. 긴 줄을 자른 뒤 Overflow를 보고하는 계약만으로는 잘린 JSON Protocol 메시지를 복구할 수 없습니다.
- **요청:** 스트림 항목에 Result를 사용하거나 오류 이벤트·별도 상태 경로를 정의합니다. 줄·버퍼 초과 시 중단·별도 보관·복구 중 정책을 정하고, 잘린 Protocol 줄을 정상 메시지로 해석하지 않게 합니다. 제어 결과가 불명확할 때 성공을 반환하지 않습니다.
- **호환 영향:** HOST/Provider의 소비 루프와 ResourceLimit·ProtocolParse 등 실패 매핑에 영향을 줍니다. 출력 상한 초과와 Local API 프레임 상한(REQ-007)은 다른 계층으로 구분합니다.
- **수용 시험:** 읽기 오류와 EOF, UTF-8/JSON 경계에서의 긴 줄, 버퍼 초과, 느린 소비자, 종료 직전 출력, 출력 장애 후 취소. 실패 원인·마지막 제어 상태와 종료 회수가 기록되는지 확인합니다.
- **현재 상태:** 검토 대기. 실제 출력 유실 버그가 재현됐다는 판정은 아닙니다.

### REQ-004 DecisionOutcome의 불변조건

- **관련 작업:** PH0-CONTRACT, PH0-MASTER, PH0-HOST, PH0-EXT. 통합은 PH0-INTEGRATION입니다.
- **대상:** `crates/schema/src/decision.rs`의 DecisionOutcome, `crates/schema/tests/contracts.rs`의 decision_outcome_wire_format 및 생성 Schema.
- **이유:** rejected·거부 사유 없음·task_created 효과의 조합이 수용됩니다. 기존 시험에도 거부와 Task 생성 효과가 함께 있는 예제가 들어 있습니다.
- **권장안:** rejected에는 거부 사유를 요구하고 실행 효과는 비우도록 합니다. accepted의 거부 사유 유무와 replayed의 의미도 명시합니다. 부분 집행을 표현할 필요가 있다면 일반 거부와 구분되는 계약을 먼저 정의합니다.
- **호환 영향:** 결과 타입·생성 Schema·MASTER 반환값·HOST/EXT 소비에 영향을 줍니다. 기존 Wire 형식을 유지할지 판별 가능한 결과 타입으로 정리할지는 CONTRACT가 결정 근거를 남깁니다.
- **수용 시험:** 거부 사유 누락, 거부와 실행 효과 동시 존재, accepted와 거부 사유 동시 존재를 정책에 맞게 검사합니다. 멱등 재요청은 기존 결과를 유지하고 효과를 다시 집행하지 않는지 MASTER 시험으로 연결합니다.
- **현재 상태:** 검토 대기. 실제 정책 엔진의 검증 완료를 주장하지 않습니다.

### REQ-005 인증 토큰의 Debug·로그 보호

- **관련 작업:** PH0-CONTRACT, PH0-HOST, PH0-EXT. 통합은 PH0-INTEGRATION입니다.
- **대상:** `crates/schema/src/api.rs`의 HelloParams·ApiRequest와 인증 요청 로그 경계.
- **이유:** HelloParams의 파생 Debug가 token 원문을 출력합니다. ApiRequest의 원시 params에도 같은 비밀값이 들어갈 수 있습니다.
- **요청:** 안전한 Debug 구현·비밀값 래퍼·인증 요청 로깅 필터 중 적용 방식을 정합니다. HelloParams만 가린 뒤 ApiRequest 전체 출력으로 우회 노출되지 않도록 합니다. 전송에 필요한 토큰 직렬화와 진단용 마스킹을 구분합니다.
- **호환 영향:** Wire는 유지할 수 있습니다. Rust 타입이나 래퍼 변경 시 생성 Schema가 같은지 확인하고 소비 코드의 생성 방식 영향을 기록합니다.
- **수용 시험:** 실제 자격 증명 대신 가짜 토큰을 사용하여 HelloParams·원시 인증 요청·오류 진단의 출력에 원문이 없는지 검사합니다. 정상 인증에 필요한 전송 값은 유지되는지 확인합니다.
- **현재 상태:** 검토 대기. 실제 비밀정보 유출 사건으로 기록하지 않습니다.

### REQ-006 Run 이벤트 종료 규칙

- **관련 작업:** PH0-CONTRACT, PH0-HOST, 세 Provider, PH0-EXT. 통합은 PH0-INTEGRATION입니다.
- **대상:** `crates/schema/src/events.rs`, AgentAdapter::events 문서, SubscriptionCloseReason과 공통 이벤트 Fixture.
- **현재 판단:** Run별 1부터 연속 순번은 채택 가능한 기준입니다. 코드에는 지속형 프로세스가 Run보다 오래 살면 turn_finished로 끝나는 예외가 이미 있습니다.
- **요청:** 시작 실패로 프로세스가 없었던 경우, Turn 뒤 사용량·최종 출력 순서, 지속형 프로세스, 취소 접수/종료 확인, 연결 유실·결과 불명 시의 스트림 종료·재구독을 구체화합니다. 존재하지 않은 프로세스의 종료를 만들어 기록하지 않습니다. 프로세스 종료와 stdout/stderr 배출·자식 회수의 순서도 REQ-002/003과 맞춥니다.
- **호환 영향:** 새 이벤트나 의미 변경이 필요하면 Event Schema Version·Fixture·구독 소비자 영향을 기록합니다. Run 완료와 실제 프로세스 수명을 하나의 사건으로 합치지 않습니다.
- **수용 시험:** 정상 단발, 프로세스 시작 실패, 살아 있는 프로세스의 Turn 완료, 취소 경합, 종료 후 출력, 결과 불명, 재구독에서 순번을 다시 매기지 않는 경우를 포함합니다.
- **현재 상태:** 검토 대기. 항상 process_exited여야 한다는 변경을 요청하는 것이 아닙니다.

### REQ-007 Local API 주소·인증·프레임 규칙

- **관련 작업:** PH0-CONTRACT, PH0-HOST, PH0-EXT, PH0-INTEGRATION.
- **대상:** `crates/schema/src/api.rs`의 모듈 계약, Host의 주소/상태 위치 계산과 Extension의 연결 처리, MAX_FRAME_BYTES.
- **현재 판단:** Named Pipe/Unix Socket, 사용자 전용 api-token, 1 MiB 상한은 채택 가능한 방향입니다. 수치나 인증 방식을 일괄 폐기할 필요는 없습니다.
- **요청:** projectKey 정규화·해시 입력에 공통 예제를 정합니다. stateDir의 프로젝트별 분리와 찾기 규칙, 토큰 생성·교체·기존 연결·재시작 동작, 파일 권한·Pipe/Socket 접근 제어 실패 처리를 명시합니다. 프레임은 UTF-8 바이트·줄바꿈 포함 여부·초과 시 응답/연결 종료·큰 결과의 분할 또는 Artifact 참조 기준을 정합니다.
- **호환 영향:** HOST와 EXT가 서로 다르게 주소를 계산하지 않게 계약 문서·공통 시험을 먼저 고정합니다. 토큰을 URI·로그·오류 메시지에 포함하지 않습니다. 새 메서드/오류/필드가 필요하면 버전 영향을 기록합니다.
- **수용 시험:** 경로 구분자·동등 경로·Unicode 경로의 동일 키, 두 프로젝트의 토큰 분리, 인증 전 요청·잘못된 토큰·재시작, 정확한 한계/한계+1 바이트·이스케이프 JSON·부분 프레임·큰 제어 응답을 포함합니다.
- **현재 상태:** 검토 대기. 현재 상수 자체가 틀렸다는 판정은 아닙니다.

### REQ-008 DecisionContext의 권한 검사 범위

- **관련 작업:** PH0-CONTRACT, PH0-MASTER, PH0-HOST. 통합은 PH0-INTEGRATION입니다.
- **대상:** `crates/schema/src/decision.rs`의 DecisionContext·RejectionCode, Core 정책 검증에 필요한 신뢰된 조회 경계.
- **현재 판단:** 거부 코드 14종은 합리적인 시작점입니다. 그 수를 늘리는 것보다 조건·판정 순서·지원하지 않는 검사의 처리가 중요합니다. 현재 Context는 Provider·Workspace 모드·Profile ID 목록 수준입니다.
- **요청:** 이 입력으로 검사하는 최소 범위와 별도 정책 조회가 필요한 실제 경로·명령·Project/Host/Session·호출자 소유권·예산 정보를 구분합니다. 필요한 신뢰된 Resolver 또는 Snapshot 필드를 정하고, 필요한 정보가 없을 때 허용으로 간주하지 않게 합니다. 목록 검사만 수행했다면 실제 실행 권한 검증이 끝났다고 표시하지 않습니다.
- **호환 영향:** Context·정책 인터페이스를 확장하면 CONTRACT가 먼저 반영합니다. MASTER가 별도 공통 타입이나 임시 필드를 만들지 않게 합니다. 사용자 권한 상한의 교집합이라는 Spec 원칙은 유지합니다.
- **수용 시험:** 다른 Project/Host/Session 참조, 허용되지 않은 Profile, 사용자 전용 결정, 호출자·Run 불일치, 정책 조회 실패, 오래된 Epoch/Revision을 포함합니다. 해당 단계에서 미지원인 검사는 명시적으로 거부·제한합니다.
- **현재 상태:** 검토 대기. 실제 권한 우회가 실행됐다는 판정은 아닙니다.

### REQ-009 중첩 Payload의 알 수 없는 필드

- **관련 작업:** PH0-CONTRACT, PH0-MASTER, PH0-HOST. 통합은 PH0-INTEGRATION입니다.
- **대상:** DecisionPayload::parse와 중첩 TaskSpec·SessionRequest 등의 Parser/Schema, 공통 실패 Fixture.
- **이유:** 최상위 Payload에는 deny_unknown_fields가 있지만 CreateTasks 안 TaskSpec의 알 수 없는 필드는 현재 파싱됩니다. 문서의 거부 정책이 어느 경계까지 적용되는지 명확하지 않습니다.
- **요청:** 신뢰하지 않는 마스터 입력의 미정의 필드를 재귀적으로 거부할지, 특정 중첩 계약은 확장을 허용할지 명시합니다. 허용한다면 무시·보존·명시적 확장 필드 중 동작을 정하고 권한·제약을 지정했다고 오해할 수 있는 입력 처리도 확인합니다. Parser와 JSON Schema·생성 타입의 정책을 맞춥니다.
- **호환 영향:** 기존에 무시하던 필드를 거부하면 입력 호환성이 바뀝니다. 공통 타입 전체에 일괄 속성을 적용하기 전에 대상·영향과 이전 요청 처리 방침을 기록합니다.
- **수용 시험:** 최상위/Task/Agent/Workspace/Session의 중첩 미정의 필드, 잘못된 필드 이름·타입, 허용한 확장과 거부한 권한 관련 입력을 시험합니다.
- **현재 상태:** 검토 대기. 무조건 모든 중첩 필드를 거부하라는 확정 결정은 아닙니다.
