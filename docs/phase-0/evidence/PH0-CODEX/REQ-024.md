§1~§7은 단계 A 제안·기준 검사 기록입니다. 승인된 계약의 구현과 최종 검증은 §8에 기록합니다.

## 1. 권장안과 승인 대상

**공통 키 8개를 문자열 상수와 알려진 키 목록으로 정의하는 방식 (a)를 권장합니다.** `AgentAdapter::detect()`의 `HashMap<String, Capability>`와 `UnsupportedCapability.capability: String`은 유지합니다. 같은 목록에서 `CommonCapabilityKey.schema.json`도 생성해 Extension에 수동 복제 없이 TypeScript 공통 키 타입을 제공합니다.

공통 키는 `managed_run`, `event_stream`, `cancel`, `native_resume`, `native_fork`, `send_input`, `answer_approval`, `vscode_listing`입니다. 기존 다수 Adapter의 `snake_case` 이름을 따르고, 메서드 이름·설정값·권한 조회 Port 이름을 별도 공통 키로 늘리지 않습니다.

INTEGRATION·사용자 검토 대상은 다음 세 가지입니다.

1. §3의 8개 공통 이름·의미·필수 범위.
2. §4의 문자열 상수 방식과 같은 원본에서 만드는 알려진 키 Schema·TypeScript 타입.
3. §5의 오류 값 정규화, 세부 제한은 `reason`으로 설명하는 원칙과 Provider 확장 키 규칙.

승인 후 INTEGRATION이 Spec §7.1을 먼저 개정해야 단계 B를 시작합니다. 이 문서는 제안이며 현재 코드에 새 키가 정의됐다는 뜻이 아닙니다.

## 3. 제안 공통 키·의미·필수 범위

여기서 필수는 모든 Provider의 모든 기능을 `supported`로 보고하라는 뜻이 아닙니다. 선택한 실행에 필요한 기능이 검증됐는지 확인하고, 없는 값·`unverified`·`unsupported`를 지원으로 간주하지 않는다는 기준입니다. 현 계약처럼 미확인 항목의 생략은 허용하며 생략을 `supported`로 해석하지 않습니다.

| 키 / 제안 Rust 상수 | 의미와 대응 | Phase 0 (§19.1) | Phase 1 / P0 (§19.2) |
|---|---|---|---|
| `managed_run` / `MANAGED_RUN` | `start_run`, 기본 `SessionMode::Fresh`의 Core 소유 실행 | 신규 실행·성공·실패의 필수 검증 대상 | 실행할 Provider의 기본 필수 기능 |
| `event_stream` / `EVENT_STREAM` | `events`, 정규화 이벤트·sequence·재생·종료 규칙 | 스트림·오류·구독 전 종료의 필수 검증 대상 | 실행 추적·결과 판정의 기본 필수 기능 |
| `cancel` / `CANCEL` | `cancel_run`, 취소 접수와 실제 프로세스·자식 종료 확인 구분 | 필수 검증 대상 | 실행 제어의 기본 필수 기능 |
| `native_resume` / `NATIVE_RESUME` | `start_run` + `SessionMode::Resume`·`source_session_id` | 실험·제한 기록은 필수, 지원 성공은 별도 판정 | 선택 기능. 해당 모드를 요청할 때 확인, Fresh/Capsule 대체와 구분 |
| `native_fork` / `NATIVE_FORK` | `start_run` + `SessionMode::NativeFork`·부모 세션 | 실험·제한 기록은 필수, 특히 Agy 성공은 필수 아님 | 선택 기능. 새 Native ID·계보·기준의 검증 범위 확인 |
| `send_input` / `SEND_INPUT` | `send_input`, **기존 Run/Turn의 진행 중 조정** | 선택 기능. 새 Turn은 기존 Run에 추가하지 않음 | 그 제어를 사용하는 경로에서 조건부 필수 |
| `answer_approval` / `ANSWER_APPROVAL` | `answer_approval`, 요청 ID에 대응하는 실행 중 승인 응답 | 도구 거부 검증과 별개인 선택 기능 | 실시간 승인 경로를 사용하는 경우 조건부 필수. 시작 전 승인이나 권한 부여와 동일하지 않음 |
| `vscode_listing` / `VSCODE_LISTING` | Managed 세션을 확장 목록 대상으로 만드는 수단·§7.6 설정 | Windows에서 수단 판정·화면 확인을 별도 기록. 미판정/미지원도 명시 가능 | 목록 표시 요구가 있는 경우 그 설정·Host에서 확인 |

특정 Turn 기준 Resume/Fork, Hidden 모드, 확장 실시간 갱신, 세션 소유권·잘못된 세션 복구까지 위 기본 키의 `supported` 하나로 보장하지 않습니다. 현재 각 Adapter의 상태·증거·사유를 이 요청에서 올리거나 낮추지 않습니다. `vscode_listing`의 설정별 상태 산정도 그대로 두고, 모드 제약은 사유와 실행 전 검사를 따릅니다.

## 4. 표현 방식 비교와 생성 경로

| 기준 | (a) 문자열 상수·알려진 키 목록 — 권장 | (b) `CapabilityKey` 열거형으로 Map 키 변경 |
|---|---|---|
| Trait | `HashMap<String, Capability>` 유지 | `HashMap<CapabilityKey, Capability>`로 변경 |
| 잘못된 공통 이름 방지 | 상수 사용·Contract 시험·잔여 별칭 검색으로 보장. 타입 자체는 자유 문자열 허용 | 열거형 사용 위치에서는 컴파일로 제한 |
| Provider 고유 확장 | 문자열 namespace로 추가 가능 | 닫힌 enum은 새 항목마다 공통 계약 변경. `Other(String)` 등을 넣으면 별도 직렬화·Schema 설계 필요 |
| 오류 값 일관성 | 같은 상수를 `UnsupportedCapability.capability`에 사용 | 오류 필드를 String으로 두면 별도 변환 필요. enum으로 바꾸면 오류 API까지 변경 |
| 변경량·순서 | Codex·공통 정의부터 빌드 가능. Claude·Agy는 별도 담당이 전환 가능 | 현재 `AgentAdapter` 구현 8곳(세 Provider·미지원 대역·TrackedAdapter·Core 시험 대역 3곳)을 함께 바꿔야 컴파일 가능 |
| JSON Schema·TypeScript | 상수만으로는 생성되지 않음. 아래의 동일 원본 Schema 출력 추가 | enum도 `json_schemas()`에 내보내야 생성됨. Trait만 바꾸는 것으로는 Map/키 Schema가 생기지 않음 |

권장하는 단계 B 배치:

- `crates/schema/src/capability_keys.rs`: 위 상수 8개와 `ALL` 목록. `telos_schema::capability_keys`로 공개.
- `json_schemas()`: `ALL`에서 **알려진 공통 키만** 나열한 `CommonCapabilityKey` string-enum Schema를 생성. Rust enum과 상수에 문자열을 따로 복제하지 않음.
- `schemas/CommonCapabilityKey.schema.json`: 기존 Schema 갱신 명령으로 생성·커밋.
- Extension: 기존 자동 생성으로 `src/generated/CommonCapabilityKey.ts`의 문자열 union을 얻음. 생성 스크립트·UI·Rust 의존을 추가하지 않음. 생성물은 커밋하지 않음.

이 Schema는 공통 키 카탈로그이며 전체 `HashMap<String, Capability>`의 허용 키를 닫는 Schema가 아닙니다. 기존 `Capability.schema.json`의 값 구조와 `CapabilityState`·`EvidenceLevel` 의미는 유지합니다. 향후 Capability Map을 Core API에 공개할 때는 그 Map DTO와 확장 키 처리도 별도 계약으로 정의해야 합니다. 현재 API에 없는 Map을 이번에 추가하지 않습니다.

## 5. 오류 값·확장 규칙 제안

1. 공통 기능은 `detect()`와 `UnsupportedCapability.capability`에서 같은 상수를 사용합니다. §2.2의 정규화 뒤 Codex의 `managed`·`approval` 등 별칭은 더 이상 출력하지 않습니다. 이전 별칭을 이중 보고하지 않습니다.
2. 설정값·세부 인자·권한 Port 이름은 키 뒤에 붙이지 않습니다. 예를 들어 Hidden 거부는 `capability = vscode_listing`, `reason = hidden 생성 수단 없음`; 특정 Turn Resume 거부는 `native_resume`와 기존 제한 사유로 표현합니다.
3. **한 요청의 `UnsupportedCapability`가 기본 기능 전체의 영구 미지원을 뜻하지 않습니다.** 인자·설정·정책을 함께 판단해야 합니다. Core가 한 오류를 보고 해당 Provider의 `Capability.state`를 자동으로 `unsupported`로 덮어쓰지 않습니다. 새 세부 기능 키를 이번에 만들지 않는 이유입니다.
4. `approval_authorization`은 새 Provider 기능이 아니라 신뢰된 정책의 전제 조건입니다. `answer_approval`로 분류하되 기존 사유와 Allow 권한 검사는 유지합니다. Capability가 `supported`라는 이유로 승인·파일·실행 권한을 부여하지 않습니다.
5. 미래의 Provider 고유 키는 `provider.<provider_id>.<feature>`를 사용하도록 제안합니다(예: `provider.codex.some_feature`). `<feature>`는 `snake_case`, 공통 8개는 prefix 없는 예약 이름으로 둡니다. 현재 이 namespace의 출력은 없으며 실험 기능을 새로 구현하지 않습니다.
6. 알려지지 않은 키를 공통 기능의 별칭으로 추측하지 않습니다. 문자열 Map에는 보존할 수 있지만, 공통 소비자는 이를 필수 기능 지원 근거로 삼지 않습니다. 공통 키 추가·의미 변경은 CONTRACT·Spec 절차를 거칩니다.

## 6. 단계 B 전환 순서와 소유권

1. **INTEGRATION 검토 → 사용자 승인 → INTEGRATION Spec §7.1 개정**. 승인된 이름·의미·생성 방식·전환 순서를 기준으로 삼음.
2. CONTRACT 범위에서 문자열 상수·키 목록·Contract 시험·Schema 출력 추가. 필수 시험: 문자열·중복 없음·카탈로그 일치, String Map의 JSON 키와 Capability 값 보존, 목록 밖 Provider 키를 보존하는 왕복. 타입을 닫지 않음을 검증.
3. Codex의 `detect()` 키 8개와 오류 7곳(`codex.rs` 6곳·`codex/run.rs` 1곳)을 공통 상수로 전환하고 소유 시험을 갱신. 상태·증거·사유 판정 보정은 C3 후속에서 수행.
4. 공통 미지원 대역의 `start_run`·`events`·`cancel_run`도 각각 `managed_run`·`event_stream`·`cancel`로 맞추는 것을 권장. **경로 조정 요청:** 권장안 (a)에서도 `crates/adapters/src/unimplemented.rs`·`crates/adapters/tests/unimplemented.rs`를 단계 B에 포함하도록 INTEGRATION이 배정을 확인해야 함. 요청서가 이 경로를 명시한 것은 방식 (b) 항목이므로 임의 수정하지 않음.
5. Claude·Agy는 각 담당이 공통 상수를 사용하고 남은 `start_run` 오류 값을 전환. Claude는 사용자 결정대로 REQ-024 단계 B 통합 뒤 C2·C4와 함께 수행. Agy는 별도 담당에게 전환 배정. 방식 (a)는 이 과도기에도 전체 컴파일을 유지하지만, 전환 완료 전 모든 Provider가 상수를 사용한다고 표시하지 않음.
6. INTEGRATION이 전체 키·오류 값 전환을 대조하고 계약 기준을 갱신. Core·Extension은 아직 키를 집행하지 않으므로 당장 소비 코드를 변경할 필요 없음. 새로운 Core 조회·집행을 시작하기 전에 전환 완료를 확인.

사용자 후속 지시(2026-10-26): **REQ-024 전체를 마친 뒤 [PH0-CODEX Capability 후속](../PH0-INTEGRATION/CODEX_CAPABILITY_FOLLOWUP.md) X1~X5를 수행**합니다. 그 작업은 별도 `ph0/codex-capability`에서 플랫폼별 판정 보정·steering·승인 Allow/Deny 실환경 시험을 다룹니다. 현재 단계 A에서 해당 판정을 바꾸거나 계정 시험을 실행하지 않았습니다.

### 8.3 남은 전환과 인계

- 승인된 단계 B 범위는 완료했습니다. `CapabilityState`·`EvidenceLevel`·`Capability` 값 구조, Trait·오류 필드 타입과 Core 집행은 그대로입니다. Cargo·Lockfile·의존성·Spec 변경도 없습니다.
- Claude·Antigravity는 기존 키 문자열을 그대로 사용하고, 두 Adapter의 CLI 미구성 오류 `start_run`도 이번에 수정하지 않았습니다. 승인된 순서대로 **단계 B 통합 뒤** 각 담당이 상수 사용과 오류 값을 전환합니다. 전체 Provider의 전환이 끝났다고 표시하지 않습니다.
- PH0-CONTRACT를 `review`로 제출하고 INTEGRATION에 Schema·열린 Map 의미·Codex 판정 보존·공통 대역 전환 검토, 병합·계약 기준 갱신을 요청합니다. Worktree·Branch는 검토용으로 보존합니다.
- 사용자 지시의 PH0-CODEX C3 작업은 이 계약 작업 다음 순서로 유지합니다. 최신 통합 계약을 기준으로 별도 Branch `ph0/codex-capability`에서 이어갈 수 있도록, 이번에는 판정 보정이나 실계정 시험을 섞지 않았습니다.
