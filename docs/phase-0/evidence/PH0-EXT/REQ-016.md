## 1. 구현

### 1.1 재연결

`extension/src/core.ts`의 최초 연결과 재연결 처리를 `useClient`로 모았습니다. 인증과 첫 유효한 Health 조회까지 성공하면 연속 실패 횟수를 0으로 초기화합니다. `degraded`도 유효한 연결입니다. 인증만 성공하고 Health 조회에 실패하면 초기화하지 않습니다.

최대 5회와 250·500·1000·2000·4000ms Backoff는 유지합니다. 기존 연결의 늦은 종료가 새 연결을 지우지 않도록 generation과 client 소유권을 함께 검사합니다. Health 대기 중 연결을 해제하면 늦은 응답으로 상태나 Heartbeat를 되살리지 않습니다.

### 1.2 Heartbeat 출력

`extension/src/extension.ts`에서 Health 응답마다 화면을 갱신하되, 출력 창에는 `phaseName`이 바뀔 때만 상태를 기록합니다. 같은 `degraded` 안에서 구성 요소 상태만 바뀌어도 TreeView는 갱신됩니다. 전체 Health가 `ok`로 바뀌거나 연결이 끊겼다가 복구되면 출력합니다.

### 1.3 구독 분배

Core의 `crates/core/src/api/server.rs`는 구독 응답을 먼저 송신 대기열에 넣은 뒤 재생 작업을 시작합니다. 기존 Extension은 Promise의 `await` 이후에 구독 ID를 설정하므로, 같은 데이터 묶음 안에서 뒤따르는 알림이 먼저 처리될 수 있었습니다. 이 틈을 메우던 각 RunFeed의 64개 임시 대기열에 다른 구독 알림까지 들어가 상한을 소모했습니다.

`extension/src/client.ts`의 요청에 선택적 응답 처리 함수를 추가했습니다. 요청 ID·응답 검사를 마친 뒤 Promise를 완료하기 전에 호출하므로 다음 알림 프레임을 해석하기 전에 구독 ID를 연결합니다. 함수에서 발생한 오류는 해당 요청을 거부합니다.

`extension/src/runFeed.ts`는 이 경로로 구독 ID를 연결하고 임시 대기열을 제거했습니다. 구독 ID가 없는 동안 다른 구독 알림을 무시하며, 이후에는 해당 subscriptionId만 처리합니다. `runId`가 없는 종료 알림도 같은 방식으로 분배합니다. Core API나 Schema 변경은 없습니다.

임시 대기열을 키우거나 무제한 대기열로 바꾸지 않았습니다. 기존 프레임 1 MiB·대기 요청 32개·Output 256 KiB 제한과 sequence·커서 유실 검사, 수신 위치부터의 재구독을 유지합니다. 단일 데이터 묶음의 정상 재생이 64개를 넘는 경우에도 임시 대기열 없이 순차 처리합니다.

## 2. 기존 빌드의 실패 재현

새 회귀 시험 중 세 항목을 기존 main의 빌드에 적용했습니다. Worktree의 수정 빌드는 임시 폴더에 보관한 뒤 시험 종료 시 복원했습니다. 추적 소스는 교체하지 않았습니다.

| 시험 | 기존 빌드 결과 |
|---|---|
| `six separate outages each recover and reread the rotated token` | 실패: 6회 장애·복구를 완료하지 못하고 `state timeout` |
| `foreign traffic while opening and same-chunk replay need no speculative queue` | 실패: 타 구독 알림 처리 중 임시 대기열 상한으로 중단. 시험 실패 콜백의 예외가 transport까지 전파되어 최종 `protocol` 거부 |
| `repeated Health refreshes update the view and log only status transitions` | 실패: 기대 1줄에 같은 `연결됨 (degraded)` 6줄 출력 |

명령: `node --test --test-name-pattern='six separate outages|foreign traffic while opening|repeated Health refreshes' test/core.test.cjs test/feed.test.cjs test/ui.test.cjs`. 3개 실패, 종료 코드 1. 임시 복원물: `%TEMP%/telos-req016-baseline-7a4e347cd67e450fa3058c071d9518de`.

## 4. 한계와 인계

- Provider 실환경 실행, Linux·Remote SSH는 이번 검증에 포함하지 않았습니다.
- Rust·공통 계약·RN 코드를 변경하지 않았으며 Rust 전체 시험은 이번 작업에서 재실행하지 않았습니다.
- 구독 분배는 현재 Core의 응답 선행 순서를 사용합니다. 알림 선행을 허용하는 다른 Protocol을 지원한다는 의미는 아닙니다.
- REQ-016 채택·완료 판정과 PH0-EXT의 integrated/verified 전환, main 병합·병합 후 정리는 기존 INTEGRATION 담당의 후속 작업입니다. 이 문서는 구현·검증 결과의 검토 인계입니다.
