## 프로젝트 개요

### 기본 정보
- **프로젝트명**: TelosWeaver (구 `rust-multi-cli-harness`)
- **버전**: 0.1.0
- **에디션**: Rust 2021
- **목적**: 다중 CLI 도구를 중앙집중식으로 관리하고 오케스트레이션하는 플랫폼

### 주요 기능
1. **도구 오케스트레이션**: 여러 CLI 도구의 실행 순서를 관리
2. **감독자 기반 의사결정**: 상위 감독자가 작업 흐름을 제어
3. **웹 대시보드**: Axum 기반의 실시간 웹 인터페이스
4. **TUI 인터페이스**: Ratatui 기반의 터미널 사용자 인터페이스
5. **상태 관리**: 도구 실행 상태 및 회로 차단기 패턴 구현
6. **메시지 시스템**: 도구 출력을 구조화된 메시지로 변환 (Rhai 스크립트)

### 기술 스택
**핵심 의존성**:
- tokio: 비동기 런타임
- axum: 웹 프레임워크 (WebSocket 지원)
- ratatui: TUI 렌더링
- rhai: 동적 스크립트 평가
- serde/serde_json: 데이터 직렬화
- chrono: 시간 처리
- uuid: 고유 ID 생성

### 주요 아키텍처 특징

#### 1. 이벤트 기반 통신
- broadcast 채널로 메시지 브로드캐스팅
- TUI와 웹 서버가 동시에 상태 수신
- 비동기 메시지 처리로 성능 최적화

#### 2. 감독자 패턴
- 외부 감독자(Codex, Copilot, Antigravity CLI) 호출
- JSON 기반 의사결정 (is_done, actions)
- 레거시 호환성 (next_tool + tool_args)

#### 3. 상태 머신 설계
- Idle -> Running -> (ErrorRecovering/PausedForIntervention) -> Idle
- 회로 차단기 패턴으로 반복 오류 감지

#### 4. 동적 파서 시스템
- Rhai 스크립트 기반 도구 출력 파싱
- 도구별 커스텀 파싱 로직
- 런타임 에러 처리 및 검증

#### 5. 프로세스 관리
- Windows/Unix 간 크로스플랫폼 지원
- stdout/stderr 동시 캡처
- 텍스트 출력 자동 압축 (최대 4,000자/라인, 100줄)

### 테스트 커버리지 분석

#### ✅ 충분히 커버되는 영역

1. **설정 파싱** (config_parse.rs)
   - TOML 파일 파싱 및 검증
   - 도구 정의 및 감독자 설정 확인

2. **상태 관리** (state_init.rs)
   - 도구 라이프사이클 추적
   - 회로 차단기 기능 (반복 오류 감지)
   - 상태 전이

3. **핵심 실행 로직** (execution.rs, orchestration.rs)
   - Rhai 스크립트 파싱
   - 도구 실행 및 출력 캡처
   - 감독자 의사결정 흐름
   - 워커 액션 처리

#### ❌ 테스트되지 않는 영역

1. **TUI 렌더링** (tui.rs)
   - 대부분 렌더링 로직 (화면 출력)
   - 사용자 입력 처리 (테스트 어려움)
   - **권장**: 수동 테스트 또는 E2E 시나리오

2. **웹 서버** (web.rs)
   - WebSocket 핸들러
   - 상태 API 엔드포인트
   - **권장**: 통합 테스트, curl/웹 클라이언트 검증

3. **오류 처리 엣지 케이스**
   - 프로세스 타임아웃 발생 시나리오
   - 잘못된 Rhai 스크립트 처리
   - 감독자 응답 파싱 실패
   - 네트워크 오류 및 파일 시스템 오류

4. **동시성 시나리오**
   - 대량 병렬 도구 실행
   - 채널 백프레셔(backpressure)
   - 경합 조건(race condition)

5. **메인 루프 통합** (main.rs)
   - 전체 애플리케이션 라이프사이클
   - TUI와 웹 서버 동시 실행
   - 정상 종료 및 에러 복구

### 테스트 커버리지 평가
- **현재 커버리지**: 약 35-40% (핵심 모듈만 테스트)
- **적절한 수준**: 프로토타입 단계로는 충분하나 프로덕션 배포 전 개선 필요

## 코드 품질 평가

### 긍정적 측면 ✅

#### 1. 구조화된 모듈화
- 관심사 분리(SoC) 잘 구현
- 각 모듈의 책임이 명확
- 공개 API 최소화 (lib.rs에 명시적 export)

#### 2. 에러 처리
- 커스텀 에러 타입 정의 (ExecutionError, OrchestrationError, ConfigLoadError)
- Result 타입 광범위 사용
- Display 트레이트로 사용자 친화적 에러 메시지

#### 3. 비동기 설계
- Tokio의 구조화된 동시성 (JoinSet, tokio::select!)
- 채널 기반 통신으로 안전한 스레드 간 데이터 공유
- 타임아웃 처리 구현

#### 4. 설정 유연성
- TOML 기반 설정으로 사용자 정의 용이
- Rhai 스크립트로 도구별 파싱 로직 동적 구성
- 감독자 및 워커 도구 교환 가능

#### 5. 크로스플랫폼 지원
- Windows 창 숨기기 처리
- Unix/Windows 호환 코드 작성

### 부정적 측면 및 우려 사항 ⚠️

#### 1. 충분하지 않은 문서화
- Rustdoc 주석 전무
- 모듈 레벨 설명 부족
- 사용 예시 없음

#### 2. 하드코딩된 상수
- MAX_CAPTURED_LINE_CHARS = 4,000
- MAX_CAPTURED_LINES = 100
- MAX_CAPTURED_CHARS = 120,000
- 설정 파일에서 지정 불가능

#### 3. 제한된 로깅
- eprintln!만 사용 (프로덕션 급 로거 없음)
- 구조화된 로깅(structured logging) 미지원
- 디버깅 어려움

#### 4. 감독자 요청 유효성 검사 부족
- JSON 파싱 실패 시 세부 정보 부족
- 필드 누락 감지 한정적

#### 5. 메모리 누수 위험
- 무한 context_log 축적
- 오류 발생 시 메모리 해제 미보장
- 장시간 실행 시 메모리 증가 우려

#### 6. 타입 안전성 약화
- String 기반 약한 타입 검증
- NewType 패턴 미사용

## 잠재 리스크 분석

### 1. 🔴 **높은 리스크**

#### A. 메모리 누수 (context_log 무한 증가)
**심각도**: High  
**발생 조건**: 애플리케이션 장시간 실행 (수일 이상)  
**영향**: 점진적 메모리 사용량 증가, OOM 종료 가능  

메시지 추가는 있으나 자동 정리 메커니즘 없음. AppState의 context_log 벡터가 계속 증가만 함.

**완화 방안**:
- 원형 버퍼(circular buffer) 도입
- 메시지 필터링 (불필요한 DEBUG 레벨 제거)
- 정기적 로그 롤오버

---

#### B. 감독자 응답 파싱 실패 시 복구 부족
**심각도**: High  
**발생 조건**: 감독자(Codex/Copilot) 비정상 응답  
**영향**: 오케스트레이션 중단, 애플리케이션 뻗음  

- 재시도 로직 없음
- Fallback 동작 부재

**완화 방안**:
- 지수 백오프 재시도
- 기본 감독자 구현 제공
- 타임아웃 후 안전한 기본값

---

#### C. 프로세스 좀비(Zombie Process) 생성 가능성
**심각도**: Medium-High  
**발생 조건**: 도구 프로세스 강제 종료 시 자식 프로세스 관리 미흡  
**영향**: 시스템 리소스 누수  

**완화 방안**:
- 프로세스 그룹 관리 (setpgid)
- 자식 프로세스 재귀 종료
- nix 크레이트로 더 견고한 제어

---

### 2. 🟡 **중간 리스크**

#### A. TUI/웹 서버 패닉 처리 미흡
**심각도**: Medium  
**발생 조건**: 렌더링 오류, WebSocket 오류  
**영향**: 애플리케이션 중단 (TUI는 계속, 웹은 다운)  

web.rs에서 unwrap() 사용:
\\\
ust
let listener = tokio::net::TcpListener::bind(&addr).await.unwrap();
axum::serve(listener, app).await.unwrap();
\\\

---

#### B. 경합 조건(Race Condition) 가능성
**심각도**: Medium  
**발생 조건**: 여러 워커 동시 실행 + 상태 쓰기 충돌  
**영향**: 상태 불일치, 예기치 않은 동작  

---

#### C. 도구 타임아웃 기본값 경직
**심각도**: Medium  
**발생 조건**: 느린 시스템, 복잡한 도구 실행  
**영향**: 정당한 작업 조기 종료  

main.rs에서 고정값 60초 사용.

---

### 3. 🟢 **낮은 리스크**

#### A. 설정 파일 미지정 시 명확한 오류 메시지
✅ **Good**: 적절한 오류 처리

#### B. Rhai 스크립트 샌드박스
✅ **Good**: \--sandbox read-only\ 플래그 사용

## 개선 제안

### Phase 1: 긴급 개선 (즉시)

#### 1. 메모리 누수 방지
AppState.context_log를 VecDeque로 변경하고 크기 제한:

\\\
ust
use std::collections::VecDeque;

pub struct AppState {
    pub context_log: VecDeque<HarnessMessage>,
    max_log_size: usize,
}

impl AppState {
    fn push_context(&mut self, msg: HarnessMessage) {
        self.context_log.push_back(msg);
        if self.context_log.len() > self.max_log_size {
            self.context_log.pop_front();
        }
    }
}
\\\

#### 2. Rustdoc 주석 추가

#### 3. 웹 서버 에러 처리 개선
\\\
ust
pub async fn start_web_server(...) {
    let listener = match tokio::net::TcpListener::bind(&addr).await {
        Ok(l) => l,
        Err(e) => {
            eprintln!("Failed to bind: {}", e);
            return;
        }
    };
    
    if let Err(e) = axum::serve(listener, app).await {
        eprintln!("Web error: {}", e);
    }
}
